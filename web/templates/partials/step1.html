What's your priority?

ServeIt Studio benchmarks real deployments on your cluster and recommends the best configuration for your model and workload. Start from what you want to optimize — or jump straight to a known architecture below.

Maximize Throughput

Find the configuration that serves the most requests per second. Best when serving many concurrent users.

Tests: Aggregated vs Expert Parallel (EP), including multi-node when available — the winner is recommended

Minimize Response Time

Find the configuration with the fastest time-to-first-token. Best for interactive and agentic workloads where users wait for the first reply.

Tests: Aggregated vs Prefill/Decode split (PD) — the winner is recommended

Full Coverage

Test every TP-based architecture and compare them all — the most thorough (and longest) option.

Tests: Aggregated, PD, and EP — three-way comparison picks the overall winner. DPEP is tested separately (below)
— OR if you already know which architecture to use —

Aggregated Only

One engine replicated across all GPUs — the simplest architecture. Fastest option to test: no architecture comparison, just the best TP size.

Architecture: Aggregated

Prefill/Decode Only

Separate GPU groups for input processing (prefill) and token generation (decode), with KV-cache transfer between them. Skips the Aggregated baseline.

Architecture: Prefill/Decode (PD)

Expert Parallelism Only

PD split with MoE expert layers distributed across GPUs instead of replicated. For Mixture-of-Experts models only.

Architecture: Expert Parallelism (EP)

DPEP Only

Independent GPU workers, each holding the full attention weights and a slice of the MoE experts (TP=1). No TP all-reduce. Matches production deployments for large MLA MoE models (e.g. GLM-5.3).

Architecture: Data Parallel + Expert Parallel (DPEP)
— OR run a specific configuration —

Single Test

Deploy one exact configuration — architecture, TP, and pod count — benchmark it, and report. No sweeps, no optimization.

Best For: Validating a known-good config or re-testing a recommendation

Soak Test

Deploy once and run the same workload N times — pods are never restarted. Catches memory leaks, CPU drift, and degradation over time. Per-cycle GPU profiles (torch traces), EPP CPU/heap profiles, and pod resource snapshots track drift across cycles; long tests use two-pass profiling so trace exports never contaminate the measurement.

Best For: Stability validation, leak detection, pre-release soak testing
🔬
Run in BLIS Simulation
Execute tests in the Blackbox Inference Simulator (CPU-only, on the target cluster's workload pod) instead of deploying GPU pods. Your EPP config and workload definition run through the embedded llm-d router — results are estimates (median 7–9% error), best for configuration ranking and capacity planning. Requires a BLIS-catalogued model (GLM-5.x, DeepSeek-V4, Kimi-K3, Llama…).
