Scoring Plugins
PluginEnableWeight
prefix-cache-scorer
Routes to pods that already have parts of the prompt cached in GPU memory.
kv-cache-utilization-scorer
Favors pods with more free GPU memory for KV cache (can handle longer sequences).
queue-scorer
Favors pods with shorter request queues. Prevents overloading a single pod.
slo-scorer
Uses predicted latency to route requests to pods that can meet the SLO target. Requires latency SLA to be enabled.
precise-prefix-cache-scorer
Tracks KV cache state in real time for exact prefix match scoring. More accurate than approximate prefix-cache-scorer but higher overhead.
active-request-scorer
Scores pods by number of in-flight requests. Load-aware alternative to queue-scorer that tracks actively processing requests.
no-hit-lru-scorer
For cold requests with no cache hits, ranks pods by least-recently-used to spread load across underutilized pods.
session-aware-scorer
Routes requests from the same session/user to the same pod for better cache reuse across a conversation.
Smart EPP Tuning
Mathematically derive optimal routing weights from your workload profile and measured cache hit rates. Typically 1-2 tests instead of 3-4.
Derives EPP routing weights from calibration data and actual benchmark metrics. Each weight is proportional to the time impact of optimal routing on that dimension (prefix cache, KV memory, queue depth).

How it works:
1. DeriveCompute weights from ISL/OSL, TP calibration data, and measured cache hit rates from Step 6/7
2. TestRun one benchmark with the derived weights (only gateway configmap swap, no pod redeployment)
3. RefineOn OpenShift: read actual metrics, adjust weights if needed, validate with one more test
Note: On OpenShift with Prometheus, weights are derived from actual measured cache hit rates and per-pod KV/queue metrics — highest accuracy. On vanilla Kubernetes without Prometheus, weights are estimated from the configured prefix cache percentage — still better than preset guessing, but less precise.
The winning weights are automatically applied before the latency search (Step 10) so throughput results reflect optimal routing.
